# Nowhere Fast

Планировщик путешествий. Статический фронтенд, данные — в Supabase.

## Состояние проекта

**Ранняя стадия.** Продуктовое видение зафиксировано в
[docs/PRODUCT-BRIEF.md](docs/PRODUCT-BRIEF.md) — читай его перед любой продуктовой
работой. Принятые решения — в [docs/adr/](docs/adr/README.md):

- **ADR-0002** — объём первой версии и анти-цель
- **ADR-0003** — источники данных о местах и ограничение на ИИ
- **ADR-0004** — место как самостоятельная сущность с координатами

Не додумывай продуктовые решения за владельца: то, чего в брифе и ADR нет, спрашивай.
Открытые вопросы перечислены в конце брифа.

## Стек

- Чистый HTML/CSS/JS, без сборки и без фреймворка
- Supabase через CDN-клиент `@supabase/supabase-js@2`, запросы идут **прямо из браузера**
- Страницы открываются как статика; публикуются на GitHub Pages из `main`
- Скрипты подключаются классическими тегами, не модулями, — чтобы страницы
  открывались и с `file://`
- npm нужен только для тестов (`npm install && npm test`), в продакшен не попадает

## Модель данных

```
cities ──┬─> places                                    (ADR-0004)
         └─> route_templates → days → activities ──> places
```

`places` — основная сущность планировщика. Координаты обязательны: место без них
неразмещаемо и в план не попадает. Поля `name_local` и `address_local` хранят
написание на языке страны — латиницу навигатор может не найти.

Схема лежит в `supabase/schema.sql`. Она **реконструирована по коду**, а не выгружена
из базы, поэтому расхождения возможны; миграция написана аддитивно и данные не трогает.

## Технический долг

Закрыто:

- ~~XSS во всех страницах~~ — вывод идёт через `assets/js/dom.js`, покрыт тестами
- ~~`app.css` не подключён~~ — подключён, inline-дубли убраны
- ~~N+1 в `city.html`~~ — один вложенный запрос с запасным путём
- ~~Поиск города по имени~~ — по `id`; поиск по имени оставлен для старых ссылок
- ~~Хардкод «Гуанчжоу»~~ — убран вместе с выдуманными тегами
- ~~Нет схемы в репозитории~~ — `supabase/schema.sql`

Открыто:

1. **Записи не защищены.** `supabase/policies.sql` написан, но **не применён**.
   Пока не применён, любой посетитель может писать в базу из консоли браузера.
   Применение отключит запись из админки до появления Supabase Auth.
2. **Нет аутентификации.** Без неё не работают ни админка после применения политик,
   ни авторство мест, ни «Мои поездки».
3. **Планировщика ещё нет.** Места с координатами есть — связывания в маршрут нет.
   Это и есть основная гипотеза продукта (ADR-0002).
4. **Старые активности не связаны с местами.** Поле `place_id` добавлено,
   но существующие строки хранят текст и в планировании не участвуют.
5. **Админка не редактирует**, только добавляет и удаляет. Города через UI не заводятся.

## С чего начинать

Порядок работы описан в [.claude/rules/development-workflow.md](.claude/rules/development-workflow.md).
Коротко: «зачем» зафиксировано в `docs/PRODUCT-BRIEF.md`; дальше — критерии приёмки
(`intent-driven-development`), план, код.

**Суть продукта одной строкой:** боль не в том, что человек не знает, *что*
посмотреть, а в том, что он не знает, *в каком порядке* — и теряет дни на возвраты,
крюки и простои. Всё остальное вторично.

## Правила

Все правила проекта — в [.claude/rules/](.claude/rules/README.md). Ключевое:

- Пользовательские данные **никогда** не идут в `innerHTML` — только `textContent`
- Единственная реальная граница безопасности — RLS на стороне Supabase,
  а не то, что скрыто в интерфейсе
- Продуктовые ограничения не выводятся из кода — только от владельца проекта
- Архитектурные развилки фиксируются в `docs/adr/`
- Перед коммитом — `npm test`; первый тест закрывает экранирование не случайно
