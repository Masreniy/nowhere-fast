# Порядок работы

> Адаптировано из ECC `rules/common/development-workflow.md` (MIT). Убраны шаги,
> завязанные на инструменты, которых у нас нет (`gh search`, Context7, Exa), и
> TDD как обязательный шлюз (см. `testing.md`). Добавлен шаг 0 — фиксация «зачем»,
> потому что на нашем этапе это главная недостающая вещь.

## Основной принцип

Сначала понять **зачем**, потом **что именно должно стать правдой**, и только
потом писать код. На каждом шаге остаётся письменный артефакт — чтобы решение
пережило сессию и не пришлось вспоминать его заново.

## Шаги

### 0. Зачем — до всего остального

Если продуктовое видение не зафиксировано, работа начинается с него, а не с кода.

Инструмент: скилл **product-lens** → артефакт `docs/PRODUCT-BRIEF.md`.

Жёсткое правило: **продуктовые и бизнес-ограничения нельзя вывести из кода.**
Репозиторий говорит, как система ведёт себя сегодня, но не что требует бизнес.
Целевая аудитория, приоритеты, сроки, модель монетизации, политика хранения
данных — только от владельца проекта. Пока не сказано — это допущение, а не факт.

### 1. Что именно должно стать правдой

Перед нетривиальным изменением — критерии приёмки: наблюдаемые, проверяемые,
с явными границами «в объёме / вне объёма».

Инструмент: скилл **intent-driven-development**.

Формулировки «работает корректно» и «безопасно» не принимаются, если не сказано,
чем это подтверждается.

### 2. План

Для многошаговой работы — агент **planner**: разбивка на этапы, зависимости,
риски, порядок. Каждый этап должен быть поставляемым сам по себе.

Для архитектурных развилок — агент **architect**.

### 3. Реализация

Тонкими вертикальными срезами: один сквозной путь целиком, а не «сначала все
модели, потом все страницы».

### 4. Проверка

Ручная проверка с описанием (см. `testing.md`), затем агент **code-reviewer**.
Если затронуты данные, права или вставка в разметку — ещё и **security-reviewer**.

### 5. Фиксация решения

Если по пути было выбрано между альтернативами — записать ADR
(скилл **architecture-decision-records**, каталог `docs/adr/`).

Причина: в этом репозитории уже есть решения, принятые молча. Например, из
`docs/FOUNDATION.md` видно, что пароль в JavaScript убрали как небезопасный, но
нигде не записано, что пришло на замену — и не пришло ничего.

### 6. Коммит

По правилам из `git-workflow.md`.

## Повторное использование

Перед тем как писать что-то с нуля, проверить, нет ли готового проверенного
решения. Для экранирования, разбора дат, валидации — почти наверняка есть.
Своя реализация оправдана, когда зависимость дороже кода.
