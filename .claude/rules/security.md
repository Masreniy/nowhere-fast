# Безопасность

> Адаптировано из ECC `rules/common/security.md` (MIT). Добавлен раздел
> «Специфика Nowhere Fast» — он описывает реальные дыры, которые у нас есть сейчас.

## Обязательный чек-лист перед любым коммитом

- [ ] Нет захардкоженных секретов (service-role ключи, пароли, токены)
- [ ] Весь пользовательский ввод валидируется
- [ ] Нет строковой конкатенации в SQL — только параметризованные запросы
- [ ] Нет XSS: пользовательские данные не попадают в HTML без экранирования
- [ ] Права доступа проверяются на сервере, не в браузере
- [ ] Сообщения об ошибках не раскрывают внутренности системы

## Управление секретами

- НИКОГДА не хардкодить секреты в исходниках
- Разделять `publishable` (анонимный, предназначен для браузера) и `service_role`
  (полный доступ, **никогда** не должен попадать во фронтенд)
- Ротировать любой ключ, который мог утечь

## Специфика Nowhere Fast

Наш фронтенд — статический HTML, который ходит в Supabase напрямую из браузера.
Это значит: **весь код фронтенда публичен, и любой запрос из него может быть
подделан**. Отсюда три жёстких правила.

### 1. Единственная граница безопасности — это RLS

**Статус на 16.09.2026: RLS включён на всех таблицах, политики применены.**
Сверено через MCP-коннектор Supabase, а не по коду. Чтение публично (города — все,
места и маршруты — только опубликованные). Записи нет ни у кого: единственный путь
к ней — вход автора, а Supabase Auth ещё не подключён. Отчёт линтера Supabase
по безопасности пуст. В базе остались только пять таблиц целевой модели: четыре
таблицы-наследия, включая `users` с колонкой `password_hash`, удалены.

Отдельный урок: до 16.09.2026 в документах было записано, что политики не применены
и «любой посетитель может писать в базу». Это оказалось неправдой в обе стороны —
чтение было открыто шире задуманного (ручные политики `using (true)` показывали и
черновики), а записи не было вообще. Утверждение о состоянии базы проверяется
запросом к базе, а не чтением файла рядом.

Нельзя полагаться на то, что страница «не показывает кнопку». Любой человек может
открыть консоль и вызвать `supabase.from('cities').delete()` напрямую. Поэтому:

- каждая таблица обязана иметь включённый RLS и явные политики;
- запись/удаление разрешены только аутентифицированным администраторам;
- проверка «пароль в JavaScript» или «скрытая ссылка на админку» — **не защита**
  (это уже зафиксировано в `docs/FOUNDATION.md`).

### 2. Никакого `innerHTML` с данными

**Статус: закрыто, держим закрытым.** Раньше все три страницы собирали разметку
строками и вставляли данные из БД и query-параметр `?city=` через `innerHTML` —
это была XSS, и отражённая, и хранимая. Сейчас `innerHTML` в страницах нет;
весь вывод идёт через `assets/js/dom.js`, покрыт тестами.

```js
// ПЛОХО — так было
container.innerHTML = `<h3>${city.name}</h3>`;

// ХОРОШО — так сейчас
NF.dom.replace(container, NF.dom.el('h3', { text: city.name }));
```

Правило на будущее: если понадобилось собрать разметку строкой — значит нужен
новый помощник в `dom.js`, а не исключение из правила на месте.

С 16.09.2026 за этим следит хук `.claude/hooks/warn-on-innerhtml.sh`: после
каждой правки `.js` и `.html` он ищет присваивание `innerHTML`/`outerHTML`,
`insertAdjacentHTML` и `document.write` — и предупреждает.

Он ищет именно присваивание, а не слово: в `dom.js` слово `innerHTML` трижды
встречается в пояснениях, и сторож, орущий на комментарии, был бы выключен
через день. И он **предупреждает, а не блокирует**: закрыть за него глаза можно,
но уже осознанно.

Исключение единственное: собственные константы проекта, которые никогда не
содержат данных пользователя (например, путь SVG-иконки из своего словаря).

### 3. Ключи в репозитории

`publishable`-ключ Supabase лежит в трёх HTML-файлах. Сам по себе он не секрет —
он спроектирован для браузера. Но:

- он обязан быть именно publishable/anon, никогда не service-role;
- при этом он бесполезен как защита, см. правило 1.

## Протокол реакции

Если найдена проблема безопасности:

1. Остановиться
2. Позвать агента **security-reviewer**
3. Починить CRITICAL до продолжения работы
4. Ротировать скомпрометированные ключи
5. Проверить весь код на такую же ошибку в других местах
