# Архитектурные решения (ADR)

Здесь фиксируются решения, которые влияют на форму проекта: выбор технологии,
схемы данных, подхода к безопасности, процесса.

Смысл не в бюрократии, а в том, чтобы через полгода можно было ответить на
вопрос «почему так, а не иначе» — и не переоткрывать уже закрытые обсуждения.

Формат — облегчённый ADR по Майклу Найгарду. Шаблон: [template.md](template.md).

## Что записываем

Технологии, архитектурные паттерны, устройство API, модель данных,
инфраструктуру, подход к безопасности, тестированию и процессу.

Не записываем: именование переменных, форматирование и прочие мелочи.

## Правила

- Записывать **почему**, а не только что — обоснование важнее решения
- Обязательно перечислять отвергнутые альтернативы: «просто выбрали» не обоснование
- Честно указывать минусы — у каждого решения есть цена
- Коротко: ADR читается за две минуты
- Отменённое решение не удаляется, а помечается `superseded by ADR-NNNN`
