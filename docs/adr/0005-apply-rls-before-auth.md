# ADR-0005: Применяем RLS сейчас, не дожидаясь аутентификации

**Дата**: 2026-09-16
**Статус**: accepted
**Участники**: владелец проекта, Claude

## Контекст

До 16.09.2026 в репозитории было записано, что политики RLS не применены и
«любой посетитель может писать в базу из консоли браузера». Проверка живой базы
через MCP-коннектор Supabase показала другое:

- RLS был включён на всех девяти таблицах;
- политик было четыре, все на чтение, все `using (true)`, заведены руками через
  интерфейс Supabase — то есть черновики тоже были видны всем;
- политик на запись не было ни одной, то есть запись была закрыта для всех,
  а не открыта для всех;
- у `places` не было ни одной политики при включённом RLS — основная сущность
  продукта ([ADR-0004](0004-places-as-first-class-entity.md)) не читалась и не
  писалась вообще.

Отдельно выяснилось, что `admin.html` не может писать в базу уже сейчас, и это
никем не было замечено: писать через админку после перехода на RLS было нечем,
а данных в `places` ноль.

Развилка: применить `supabase/policies.sql` сейчас — или ждать Supabase Auth,
чтобы админка не осталась без записи.

## Решение

Применяем `supabase/policies.sql` немедленно и снимаем ручные политики
`using (true)`. Запись остаётся доступна только аутентифицированному автору
своих записей; до появления Supabase Auth данные заводятся через интерфейс
Supabase, а не через `admin.html`.

## Рассмотренные альтернативы

### Альтернатива 1: Ждать Supabase Auth, ничего не трогать
- **За**: не создаём период, когда админка заведомо не работает
- **Против**: `places` остаётся полностью недоступной — сайт не может показать
  ни одного места, даже если их завести; черновики маршрутов видны всем
- **Почему нет**: ожидание ничего не сохраняет. Админка не пишет и так, а
  недоступность `places` блокирует единственную ценную сущность продукта

### Альтернатива 2: Открыть анонимную запись до появления Auth
- **За**: админка сразу заработала бы
- **Против**: ключ в HTML публичный, поэтому анонимная запись — это запись для
  любого посетителя, включая удаление чужих данных
- **Почему нет**: прямо противоречит правилу «единственная граница безопасности —
  RLS» (`.claude/rules/security.md`). Мы бы своими руками открыли дыру, которой,
  как выяснилось, в проекте никогда и не было

### Альтернатива 3: Оставить ручные политики `using (true)` рядом с новыми
- **За**: ничего не ломается, данные точно видны
- **Против**: разрешения RLS складываются по ИЛИ — пока жива `using (true)`,
  любая более строгая политика рядом не ограничивает ничего
- **Почему нет**: это была бы имитация защиты, худший из вариантов

## Последствия

### Положительные
- `places` читается: опубликованные места видны всем, черновик — только автору
- Состояние базы описано в репозитории и воспроизводится запуском `policies.sql`
- Черновики маршрутов больше не показываются посетителям

### Отрицательные
- `admin.html` официально не работает на запись до появления Auth. Это не регресс
  (он не работал и раньше), но теперь это зафиксировано как факт, а не как сюрприз
- Единственный способ завести данные — интерфейс Supabase

### Риски
- Supabase Auth становится блокирующей задачей: без неё база не наполняется из
  интерфейса. Смягчение: задача поднята на первое место в техдолге `CLAUDE.md`

  **Уточнение от 16.09.2026 (в тот же день):** риск сформулирован неверно и
  противоречил [ADR-0002](0002-mvp-scope-and-anti-goal.md), который вынес аккаунты
  за пределы первой версии. Блокировки нет: база наполняется через интерфейс
  Supabase и через MCP-коннектор. Заблокирован только один способ записи —
  через `admin.html`. Приоритет аутентификации в `CLAUDE.md` снят.
- Проверка политик сделана со стороны базы (`pg_policies`, линтер Supabase), а не
  из браузера: сеть рабочей среды до `*.supabase.co` закрыта политикой окружения.
  Смягчение: в конце `policies.sql` записан сценарий ручной проверки из браузера —
  он остаётся невыполненным и ждёт владельца
